# GL003 dead-policy

Default severity: **error** (**warn** for a policy on a relation the migrations never create).

## What it catches

An RLS policy created or altered in an enforced migration for a role that, at the end of that
migration, cannot use it:

- a `for select`, `for insert`, `for update` or `for delete` policy needs that privilege;
- a `for all` policy needs any one of `select`, `insert`, `update`, `delete`;
- a policy for `PUBLIC` (no `TO` clause) is dead when neither `anon` nor `authenticated` holds a
  matching privilege; `anon` and `authenticated` named in `TO` are checked one by one;
- other roles are checked only when listed in [`clientRoles`](../configuration.md#clientroles).

A policy that only admits `service_role` is not checked: every `USING` and `WITH CHECK`
expression it has is a single comparison of the request role with `'service_role'` (for example
`auth.role() = 'service_role'`; [GL002](GL002.md#what-it-catches) lists the recognised forms).
It never admits a client role, and `service_role` bypasses RLS, so it is not client access
control. The same goes for a deny-all policy, whose every expression is the constant `false`
(`using (false)`; see [GL002](GL002.md#what-it-catches)). `ALTER POLICY ... USING` or `WITH CHECK` re-evaluates this; `ALTER POLICY ... TO` alone
does not.

A policy on a relation the migrations never create is reported at warn level, because its grants
cannot be checked. When a later migration creates it, the message names that file: a replay
(`supabase db reset`, a preview branch) fails at the policy.

## Why it matters

Postgres checks table privileges before row level security. A policy for a command the role has no
privilege for never applies: the request fails with `42501 permission denied` first. It looks like
access control in review, and it does nothing. Adding a new command to an existing table (an
`insert` policy on a table clients could only read) is the usual way this happens.

## Failing example

```sql
-- supabase/migrations/20261001000000_revoke_automatic_grants.sql
alter default privileges for role postgres in schema public
  revoke all on tables from anon, authenticated, service_role;
alter default privileges for role postgres in schema public
  revoke all on sequences from anon, authenticated, service_role;
```

```sql
-- supabase/migrations/20261002120000_add_todos.sql
create table public.todos (
  id bigint generated always as identity primary key,
  user_id uuid not null default auth.uid(),
  title text not null
);
alter table public.todos enable row level security;
grant select, insert, update, delete on public.todos to service_role;
grant select on public.todos to authenticated;
create policy "Users read their todos" on public.todos
  for select to authenticated using (auth.uid() = user_id);
```

```sql
-- supabase/migrations/20261003120000_users_add_todos.sql
create policy "Users add their todos" on public.todos
  for insert to authenticated with check (auth.uid() = user_id);
```

Output of `supabase-grants-lint check`:

```text
supabase/migrations/20261003120000_users_add_todos.sql
  2:1  error  GL003  Policy "Users add their todos" on public.todos is for insert by authenticated, but authenticated holds no insert privilege on it: Postgres checks privileges before RLS, so the policy never applies and those requests fail with 42501 permission denied. Grant authenticated the privilege in the same migration, or drop the policy.
              fix   grant insert on public.todos to authenticated;
              docs  https://github.com/guptaaman678/supabase-grants-lint/blob/v0.1.0/docs/rules/GL003.md

1 error, 0 warnings  (3 files, 1 relation, 0.0s)
```

## Fix

Grant the privilege the policy needs in the same migration, or drop the policy if the role should
not have it.

```sql
-- supabase/migrations/20261003120000_users_add_todos.sql
grant insert on public.todos to authenticated;
create policy "Users add their todos" on public.todos
  for insert to authenticated with check (auth.uid() = user_id);
```

## When it is safe to disable

When a policy is kept on purpose for a role that should not have the privilege yet, for example
before a feature launches. Suppress that one policy with a reason rather than turning the rule off.
For the warn-level "unknown relation" finding: when the table is created outside the migrations
(dashboard, another tool), add an `ignore` entry for it.

## Configuration

- [`clientRoles`](../configuration.md#clientroles) adds roles to check.
- [`serviceOnly`](../configuration.md#serviceonly) exempts relations only server code uses.
- Suppress one finding with `-- grants-lint-disable-next-line GL003: <reason>` on the line above
  the `create policy` or `alter policy` statement, or an [`ignore`](../configuration.md#ignore)
  entry.
