# GL002 unreachable-new-relation

Default severity: **error**.

## What it catches

A relation created in an enforced migration that has RLS policies (created in the same migration)
for a client role, while at the end of that migration the role holds no `select`, `insert`,
`update` or `delete` privilege on it. Client roles are `anon`, `authenticated`, any role in config
[`clientRoles`](../configuration.md#clientroles), and `PUBLIC` (a policy without a `TO` clause).
For `PUBLIC`, the rule reports when neither `anon` nor `authenticated` holds a privilege.

Policies that only admit `service_role` do not count. A policy is service-role-only when every
`USING` and `WITH CHECK` expression it has is a single comparison of the request role with
`'service_role'`, for example `auth.role() = 'service_role'`,
`(select auth.jwt() ->> 'role') = 'service_role'`,
`current_setting('request.jwt.claims', true)::jsonb ->> 'role' = 'service_role'` or
`current_user = 'service_role'`. Such a policy never admits `anon` or `authenticated`, and
`service_role` bypasses RLS, so it means "no client access" and needs no client grant. An `OR`,
another role or a function call such as `is_admin()` makes it an ordinary client policy again.

Deny-all policies do not count either: every `USING` and `WITH CHECK` expression is the constant
`false` (bare, or cast with `::boolean`), as in `create policy "No direct access" on public.audit_log
for all using (false);`. Such a policy admits no row for anyone, so it means "no client access"
and needs no client grant. A mix of the two forms (for example `using (false)` with a
service-role-only `WITH CHECK`) also counts as no client access.

When GL002 reports a relation and role, GL003 findings for the same relation, role and migration
are left out: they have the same cause and the same fix.

## Why it matters

The policies show the author meant clients to use the table, but Postgres checks table privileges
before row level security. Every Data API request as that role fails with
`42501 permission denied for table`, and the policies never run. Before the change, the automatic
grants hid this; afterwards it is the most common way a new feature breaks on its first request.

## Failing example

```sql
-- supabase/migrations/20261001000000_revoke_automatic_grants.sql
alter default privileges for role postgres in schema public
  revoke all on tables from anon, authenticated, service_role;
alter default privileges for role postgres in schema public
  revoke all on sequences from anon, authenticated, service_role;
```

```sql
-- supabase/migrations/20261002120000_add_messages.sql
create table public.messages (
  id uuid primary key default gen_random_uuid(),
  sender_id uuid not null default auth.uid(),
  body text not null
);
alter table public.messages enable row level security;
grant select, insert, update, delete on public.messages to service_role;
create policy "Users read their messages" on public.messages
  for select to authenticated using (auth.uid() = sender_id);
create policy "Users send messages" on public.messages
  for insert to authenticated with check (auth.uid() = sender_id);
```

Output of `supabase-grants-lint check`:

```text
supabase/migrations/20261002120000_add_messages.sql
  2:1  error  GL002  public.messages has RLS policies for authenticated, but authenticated holds no select, insert, update or delete privilege on it: every Data API request as authenticated fails with 42501 permission denied before any policy runs. Grant authenticated the commands its policies cover in the same migration.
              fix   grant select, insert on public.messages to authenticated;
              docs  https://github.com/guptaaman678/supabase-grants-lint/blob/v0.1.0/docs/rules/GL002.md

1 error, 0 warnings  (2 files, 1 relation, 0.0s)
```

## Fix

Grant the role the commands its policies cover, in the same migration. The fix line in the output
lists them.

```sql
-- supabase/migrations/20261002120000_add_messages.sql
create table public.messages (
  id uuid primary key default gen_random_uuid(),
  sender_id uuid not null default auth.uid(),
  body text not null
);
alter table public.messages enable row level security;
grant select, insert, update, delete on public.messages to service_role;
grant select, insert on public.messages to authenticated;
create policy "Users read their messages" on public.messages
  for select to authenticated using (auth.uid() = sender_id);
create policy "Users send messages" on public.messages
  for insert to authenticated with check (auth.uid() = sender_id);
```

## When it is safe to disable

When clients really must not reach the table and the policies are there for another role you do
not list in `clientRoles`. For tables only server code uses, list them in
[`serviceOnly`](../configuration.md#serviceonly) instead of turning the rule off.

## Configuration

- [`clientRoles`](../configuration.md#clientroles) adds roles to check.
- [`serviceOnly`](../configuration.md#serviceonly) exempts relations only server code uses.
- Suppress one finding with `-- grants-lint-disable-next-line GL002: <reason>` on the line above
  the `create` statement, or an [`ignore`](../configuration.md#ignore) entry.
