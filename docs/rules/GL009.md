# GL009 drift

Default severity: **warn**.

## What it catches

Differences between a live database and what its migrations produce, found by
`supabase-grants-lint diff` and `supabase-grants-lint doctor --db-url` (see
[live mode](../live-mode.md)). `check` never connects to a database, so it never reports GL009.

In the configured [`schemas`](../configuration.md#schemas), for `anon`, `authenticated`, the roles in
[`clientRoles`](../configuration.md#clientroles), the [`serviceRole`](../configuration.md#servicerole)
and `PUBLIC`, it compares:

- the privileges on each table, view and sequence (one finding per relation, role and direction);
- relations that exist in the database but in no migration, or the reverse;
- the default privileges of [`migrationRole`](../configuration.md#migrationrole) for new tables and
  sequences (whether the database still grants new tables automatically);
- policies: ones that exist on one side only, a different command, and roles on one side only.

Every message starts with the direction: "In the database, not in the migrations" or "In the
migrations, not in the database". `maintain` is compared only on Postgres 17 and later. Relations
that belong to an extension, and identity sequences, are not compared.

## Why it matters

The migrations are what a new project, a preview branch and `supabase db reset` are built from. A
grant made by hand in the SQL editor (often to fix a `42501 permission denied` in a hurry) makes
production work while every database built from the migrations still fails. The reverse, a grant in
the migrations that the database lacks, usually means a migration was never pushed.

## Failing example

The project opted in, and the table grants only what the app needs. Later a `42501` for signed-out
visitors was fixed by running a grant in the SQL editor.

```sql
-- supabase/migrations/20261001000000_revoke_automatic_grants.sql
alter default privileges for role postgres in schema public
  revoke all on tables from anon, authenticated, service_role;
alter default privileges for role postgres in schema public
  revoke all on sequences from anon, authenticated, service_role;
```

```sql
-- supabase/migrations/20261002120000_add_todos.sql
create table public.todos (
  id bigint generated always as identity primary key,
  title text not null
);
alter table public.todos enable row level security;
grant select, insert, update, delete on public.todos to authenticated, service_role;
create policy "Anyone reads todos" on public.todos for select to anon, authenticated using (true);
```

```sql
-- run in the database (SQL editor)
grant select on public.todos to anon;
```

Output of `supabase-grants-lint diff`:

```text
supabase/migrations/20261002120000_add_todos.sql
  2:1  warn   GL009  In the database, not in the migrations: anon holds select on public.todos. A database built from the migrations (a new project, a preview branch, a local reset) will not have it: add the grant to a migration, or revoke it in the database if it was not meant.
              fix   grant select on public.todos to anon;
              docs  https://github.com/guptaaman678/supabase-grants-lint/blob/v0.1.0/docs/rules/GL009.md

0 errors, 1 warning  (2 files, 1 relation, 0.0s)
```

## Fix

Capture the change in a migration, so every database built from the migrations has it:

```sql
-- supabase/migrations/20261003090000_anon_reads_todos.sql
grant select on public.todos to anon;
```

If the change was not meant, undo it in the database instead (here, `revoke select on public.todos
from anon;`). For a relation or policy made in the dashboard, `supabase db diff` writes the
migration.

## When it is safe to disable

When the database is expected to differ, for example relations another tool manages. Prefer an
[`ignore`](../configuration.md#ignore) entry naming the relation, so drift elsewhere is still
reported. `diff` exits 0 on warnings unless you pass `--max-warnings 0`.

## Configuration

- [`schemas`](../configuration.md#schemas), [`clientRoles`](../configuration.md#clientroles),
  [`serviceRole`](../configuration.md#servicerole) and
  [`migrationRole`](../configuration.md#migrationrole) decide what is compared.
- Suppress one finding with `-- grants-lint-disable-next-line GL009: <reason>` on the line above
  the statement it is attached to, or an [`ignore`](../configuration.md#ignore) entry. Findings
  about things no migration creates are attached to line 1 of the last migration file.
